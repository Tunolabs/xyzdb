# v1.1.1 — the doors the last fix missed

**Released 2026-08-06** · **Tag**: `v1.1.1` on `main` · **Type**: patch — no
behaviour change, no on-disk format change, no wire change. A 1.1.0 data
directory opens unchanged and a 1.1.0 client keeps working. Same BUSL line as
1.1, same Change Date (2029-09-01).

## Why a patch, and what "no behaviour change" means here

Every fix below closes a path that could produce a **wrong answer** after an
unclean restart, and none of them changes what the engine does on a healthy one.
The single new response field is additive JSON. The one thing an upgrader gains
that they can see is the `version` key.

## The defect, and the shape of it

1.1.0 armoured the duplicate-anchor check on the single-`PUT` path: after a
process replays WAL, a bloom-gated "this anchor is absent" is re-confirmed
without the bloom before it is believed, because a post-recovery SSTable can
carry a filter that disagrees with its own data.

**The same decision existed in two more places and neither was armoured.** `PUT
BATCH` ran a plain bloom-gated `get`; so did the `AUTOANCHOR APPLY` back-fill.
One defect class, three doors, one closed.

What each open door cost:

| Path | A false "absent" means |
|---|---|
| `PUT BATCH` | a second record under a `UNIQUE` anchor — a duplicate ledger entry, silently |
| `AUTOANCHOR APPLY` | the value is re-indexed onto another record's LID; the anchor starts resolving somewhere else, and the step reports the write as "indexed" |
| ghost writes counter | a promotion counter resets, so a ghost that had earned auto-creation earns it again |

**The fix is the shape, not the three edits.** All three now go through one
function, `ops::put::anchor_dict_get`, which is where the confirmation, the
counter and the warning live. Three copies of a decision is exactly the mechanism
by which two of them diverged when the third was corrected; a fourth caller
cannot conclude "this anchor is free" without passing through it.

Each door has a forged-bloom test **and a negative control that asserts the
defect with the armouring switched off**. The controls paid for themselves during
development: the first draft created its collision with a fresh `PUT`, whose
dictionary entry lands in the active memtable — which has no bloom — so the filter
was never consulted and the tests passed for the wrong reason.

## A correction to `KNOWN-ISSUES.md`

That file reported a duplicate check in `DECLARE ANCHOR`. There is none:
`ANCHOR … UNIQUE IN` registers the anchor and never touches the dictionary. The
bloom-gated read was in `AUTOANCHOR APPLY`, an operational populate step. The
label mattered — it pointed readers at a declarative statement every application
issues, when the exposure is a step an operator runs by hand. The correction is
recorded in that file rather than quietly applied.

## Added

- **`version` in `STATS`, HTTP `/stats` and `/health`.** Additive and diagnostic;
  `alive` keeps its place in the health payload. Until now the only way to learn
  which engine you were talking to was `--version` against the binary inside the
  container — which an operator holding a connection cannot do, and which is step
  one of the format-mismatch procedure in `OPERATIONS.md` §8.4.
- **Two new `KNOWN-ISSUES` entries**, both filed rather than fixed because both
  fixes are behaviour changes a patch must not make: ghost deltas and the
  `AUTOANCHOR APPLY` insert are written outside the WAL (derived state only — no
  acknowledged record is lost, `REFRESH GHOST` repairs), and `/ready` reports
  not-ready on an idle engine under `--durability durable`.
- **Per-file `SPDX-License-Identifier: BUSL-1.1`** across the tree.

## Documentation: three things we asserted and the engine denies

Settled against a running engine, not by reading:

- **`LOBE` is not idempotent.** Re-declaring an existing lobe is refused with
  `INVALID_QUERY`, and so is re-declaring an anchor. The spec had promised the
  opposite. Making it a no-op is the better contract and is a behaviour change,
  so the sentence is corrected and the change waits for a minor.
- **`docs/mcp-integration.md` and the README commanded `xyzdb-mcp:1.1.0`.** GHCR
  carries `1.0.1` only. They now name the tag that exists.
- **The `ROADMAP` still called the satellite axis "design in validation".** It
  shipped in 1.1.0; what remains is re-packing records that already exist.

Also added, from an external integration exercise: a retry-safety table per
statement and the idempotent-write pattern (anchored `PUT` + `ON CONFLICT
UPDATE`), that identifiers are interpolated and only *values* can be bound, that
an upsert **merges** rather than replaces, and that a link written by the
standalone `LINK` statement is **not visible to `PULL`** — with `GRAVITY BY` on
the child lobe as the supported idiom.

## Upgrading

Stop, replace the binary or image, start. No migration, no `REFRESH GHOST`, no
configuration change. If you have a dashboard reading `STATS`, it gains one key.
