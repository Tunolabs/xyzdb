# v1.1.0 — sub-gravity, and detectors that speak

> **Number decided, tag not yet cut.** The version, the LICENSE line and the
> Change Date are bumped and `.ci/license-version-parity.sh` passes; what remains
> is to fast-forward `main` and tag `v1.1.0`.

**Branch**: `dev` · **Type**: minor — additive and backward compatible, **no
on-disk format break**, a 1.0.x data directory opens unchanged · **Tag**: not yet
cut.

## Why 1.1.0 and not 1.0.1

Not because the release is large. Because a patch number would have been wrong.
This release adds **new grammar** (`SATELLITE BY`), **new response fields**
(`budget_stop` and its `strategy`), **new `STATS` and `/metrics` surface**
(`invariant_guards`, `recovered_from_wal`), and **a new field on
`describe_lobe`** — all additive, all backward compatible. That is the definition
of a minor release. Numbering it as a patch would have hidden a feature in a
patch digit, and it also required its own BUSL line: 1.1 carries its own Change
Date (2029-09-01), separate from 1.0's.

## TL;DR

- **Sub-gravity (`SATELLITE BY`)**: a third foundational axis that splits one
  gravity bucket into sub-buckets, so a query pinning both the gravity field and
  the satellite field reads only the matching rows instead of the whole bucket.
  Opt-in per lobe; not declared = unchanged behaviour and no cost.
- **`NEAREST` no longer scores the whole bucket** when the query pins a declared
  satellite field — the query shape that motivated the whole axis.
- **A truncated `NEAREST` partial now says what it is**: `budget_stop` reports the
  counts at the cut *and* which traversal produced them, because the two kinds of
  partial license different conclusions.
- **Three correctness fixes, each of which could return a wrong answer with no
  error.** Read these before the features if you already run xyzDB:
  - **A `UNIQUE` anchor can no longer be duplicated after an unclean restart.**
    A process that came up from a dirty restart could write a second record under
    a key declared unique, silently: an idempotent insert stopped being
    idempotent, and nothing said so.
  - **`ON CONFLICT UPDATE` now reaches aggregate ghosts.** An upsert skipped the
    ghost notification, so a maintained aggregate kept serving its pre-upsert
    sums and counts.
  - **`ON CONFLICT UPDATE` now reaches the record cache.** A cached read could
    return the record as it was before the upsert — a read-your-own-write
    violation.
  - **One of them needs an action from you after upgrading**: if you have
    aggregate ghosts over a lobe that has taken upserts, run `REFRESH GHOST`
    once. See [Upgrading with ghosts declared](#upgrading-with-ghosts-declared).
- **Engine invariant guards became observable state** (`STATS` + `/metrics`)
  instead of a log line nobody was reading.

## Sub-gravity: `SATELLITE BY <field> IN "lobe"`

Gravity decides *which bucket* a record lands in. The satellite axis decides *how
one bucket is sub-divided*: the named field's value maps through a 16-bit hash to
the `sat` axis of the spatial key, so a `SCAN … WHERE gravity = g AND kind = k`
walks one sub-range rather than the parent bucket. The same shape feeding
`AGGREGATE count()` and `GROUP BY` is bounded too.

It is a **pure optimisation** — same rows, same order as the parent scan. The
16-bit hash collides by design, so the read path always re-applies the field
predicate as an anti-collision residual; correctness never depends on the hash
being unique. That equivalence is gated row-for-row, not as a set.

**Rules worth reading before declaring it** (full text in `docs/xytalk-spec.md`
§2.2.2):

- One axis per lobe, declared on an **empty** lobe.
- Leaving is free: retracting the axis loses the speed-up, never data or exactness.
- A `SET` that changes the field **re-places** the record; **`ON CONFLICT UPDATE`
  does not** (same contract gravity already had). A satellite field mutated
  through an upsert strands the record where a bounded query cannot see it, and a
  bounded `count` over the new value then runs **silently short**. Pick an
  immutable axis field, or mutate with `SET`.
- Records missing the field share satellite 0, so the axis pays only when the
  field is near-universal in the lobe.
- Values that render alike share a satellite (`Int(5)`, `Float(5.0)` and `"5"` all
  canonicalise to `"5"`). Harmless — the residual separates them by type — but it
  makes the axis coarser than the field's distinct values.

The on-disk cost was measured before building: at product cardinality (5–20
distinct values) the parent scan reads **−4.5 % to −7.5 % bytes**, i.e. same-value
grouping compresses slightly better. The format itself was pre-paid at 0.9.4, when
the `sat` axis was reserved while there were no users, so **no migration**.

**The axis is discoverable, not just declarable.** `SHOW PROFILE` reports it, and
the MCP `describe_lobe` tool gained a `satellite` field alongside the gravity and
vector ones. An agent that cannot see the axis cannot write the query shape the
axis exists to make cheap — leaving it out would have shipped an optimisation
nothing knew how to ask for.

## `NEAREST` bounded by the satellite

With an equality on the satellite field the candidate set **is** the satellite, so
scoring within it is the exact top-k of the filtered set rather than an
approximation. Previously a highly selective residual forced descending the whole
bucket in score order — the case that could take seconds. This is the query that
motivated sub-gravity, and it now reads only its sub-range.

## `budget_stop`: what a truncated partial actually is

A `NEAREST` cut by the latency airbag (`--nearest-budget-ms`) returns
`PaginatedRecords { has_more: true, cursor: None }` — prefix-correct, never an
error. It now carries `budget_stop`:

| Field | Meaning |
|---|---|
| `candidates` | the whole **scored** set (the bucket), before the residual — **not** the number of matches |
| `examined` | how many had the residual **checked** before the cut |
| `found` | how many **passed** |
| `strategy` | which order produced it: `"score_order"` or `"key_order"` |

Read as *"scored C, checked the filter on E of them, F passed"*. `examined /
candidates` is the fraction of the universe checked and `found / examined` the
filter's observed pass rate, so a client can extrapolate the unchecked tail
itself — an inference the client draws, not a claim the engine makes.

`strategy` exists because those two readings do not behave alike. *How many
remain* estimates under either traversal; *whether what remains is worse* holds
only under `"score_order"`, where the rows are a true prefix. Under `"key_order"`
they are the best of a contiguous key region and the unwalked part may hold
**better** rows. The field is absent from every non-truncated frame, so ordinary
pagination is byte-identical and `has_more`-keyed clients are unaffected.

**1.1.0 emits only `"score_order"`.** The second traversal is built and tested
but no shipped code path selects it — the switch that would is not in this
release, and the flag that forces it in tests has exactly one writer, the test
suite. The field ships early on purpose: a client written against this release
keys off the fact rather than assuming it, and keeps working unchanged when the
other order starts appearing. Read the `"key_order"` column as a contract, not as
something you will observe today; the release that starts emitting it will say
so.

## A `UNIQUE` anchor survives an unclean restart

The duplicate-anchor check is a bloom-gated point read, and a post-recovery
SSTable can carry a bloom that disagrees with its data — so the check could report
"absent" for an anchor that exists, and `PUT` would write a second record under a
key declared unique, silently.

The check is asymmetric, which makes the fix cheap: a false positive costs
nothing, only the **miss** branch needs armouring, and only in the window where
the defect is reachable. When a process replayed WAL at open, an anchor miss is
re-confirmed without the bloom before being trusted.

**Declared cost.** The mode lasts the whole life of a recovered process, so a
write-heavy anchored lobe pays a level descent per anchor miss until restart. It
is published rather than left to be inferred from slower writes:
`recovered_from_wal` in `STATS`, `xyzdb_recovered_from_wal` on `/metrics`.

This closes the duplicate-record exposure **independently of the underlying bloom
defect**, whose root cause remains open.

## `ON CONFLICT UPDATE` reaches what an update is supposed to reach

`PUT … ON CONFLICT UPDATE` wrote the record and then skipped two propagation
hooks that a plain insert and a `SET` both run. The record on disk was always
correct; what read it was not.

**Aggregate ghosts served stale numbers.** Without the ghost notification, a
covering ghost never refreshed and an aggregate ghost never adjusted its sums and
counts on the old→new delta. A dashboard reading `SCAN GHOST` got the totals as
they stood before the upsert — no error, no staleness marker, just an old number
presented as current. Drift accumulated across every upsert.

**A cached read returned the pre-upsert record.** Without the record-cache
write-through, a read served from cache after an upsert could hand back the
previous version of the record: a **read-your-own-write violation**, the one
guarantee a caller is least prepared to have broken. Writing and immediately
reading back could show the old value.

Both are fixed by routing the upsert through the same update template `SET`
already used (`WriteType::Update { old_record, old_spatial_key }` for ghosts,
`update_record` for the cache). The fix came out of a side-by-side sweep of
insert / `SET` / `DELETE` / upsert rather than from a report, which is also how
the record-cache half was found — it was on no list. The gate is a drift oracle:
primary versus ghost across an upsert that crosses the ghost's predicate, failing
on the pre-fix code and passing after.

### Upgrading with ghosts declared

**The fix stops new drift; it does not repair drift already recorded.** The two
halves differ in whether you need to act:

| | Survives a restart? | Action after upgrading |
|---|---|---|
| **Record cache** | No — it is in-memory only | **None.** The restart that upgrades you empties it. |
| **Aggregate ghosts** | **Yes** — ghost state is persisted | **Run `REFRESH GHOST "<name>"` once** per aggregate ghost whose source lobe has ever taken an `ON CONFLICT UPDATE`. |

`REFRESH GHOST` rebuilds from the source lobe's **current** records, never from
the ghost's own (possibly drifted) index, so one pass clears whatever error
accumulated while the bug was live. After that, no `REFRESH` is needed for
upserts — that is precisely what this fix restores. If you have no ghosts, or
only ghosts over lobes that never take upserts, there is nothing to do.

## Invariant guards became state

The L1+ non-overlap guard panicked in debug and logged in release — so it was
silent in every embedder linking the crate as a library without a `tracing`
subscriber, which is most of them. An invariant owned by the engine cannot
delegate its visibility to the caller's logging. It is now a counter in `STATS`
(`invariant_guards`, broken down per keyspace) and on `/metrics`, alongside a
counter for duplicate-anchor inserts prevented by the confirmation above. Every
known keyspace is emitted even at zero: a missing series is indistinguishable
from a scrape gap.

Also fixed: table ids are now monotonic **across restarts**, so one identity can
never name two different table contents.

## Compatibility

- **No on-disk format break.** A 1.0.x data directory opens unchanged.
- **Client drivers: compatible on the wire, but the 1.0.x line is withdrawn.**
  These are two separate statements and the second is the one that decides what
  you should do.

  *Compatible*: a 1.0.x `xyzdb` client will not break against this engine. Every
  change here is additive, and `budget_stop` rides on a frame the client already
  parses.

  *Withdrawn*: the 1.0.x clients are **yanked** on crates.io, PyPI and npm, so a
  fresh resolve will not select them. They are yanked for a reason that this
  release makes worse rather than better — their fluent terminal drops
  `budget_stop`, `has_more` and `cursor` on the way to the caller. Against a 1.1.0
  engine that means a `NEAREST` truncated by the latency airbag arrives looking
  exactly like a complete answer. "Compatible" here means *it will not error*, not
  *it will tell you the truth*.

  **Move to the 1.1.0 clients.** They surface the partial and warn when one is
  consumed unchecked; they are also what you need to *use* `SATELLITE BY`, which
  earlier engines reject as a parse error. Client and engine versions move
  independently, and that both read 1.1.0 today is coincidence, not a contract.
- **Additive wire changes only.** `budget_stop` appears solely on a truncated
  `NEAREST` frame; every other response is byte-identical.
- **`SATELLITE BY` is opt-in.** A lobe that does not declare it behaves exactly as
  before, with no code path taken and no cost.
- **New `STATS` fields** (`invariant_guards`, `recovered_from_wal`) and new
  `/metrics` series. Scrapers that enumerate fields strictly should be checked.
